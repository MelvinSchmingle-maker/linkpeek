# A headless browser could fix empty pages

Only one open-source tool could fix the empty pages, and it changes what LinkPeek's backend does. Sparticuz/chromium (MIT, 1.7k stars, last update 11 September 2026) packages a headless browser, which is a Chrome with no window, so a Vercel function could load a page the way a visitor's browser does and return its text. Today the backend never receives a page's address, because it only takes article text for summaries, so this would be a new kind of data flow. The permission problem has no open-source answer, because LinkPeek already offers an all-sites grant in its settings, and the real question is whether that grant becomes the default ask. Most other failures have small, permissively licensed fits that run on the device, namely Mozilla Readability, pdf.js and a redirect rule, while consent walls and bot checks should stay failures with no tool attached. Measure how many links come back empty before building a renderer, since the project's own decision log says to revisit server fetching only if the numbers call for it. Hosted services such as Jina Reader render pages too, but they would receive every article address, and their terms may predate a recent acquisition.

## Empty pages need a server or a third party

The card says "The page needs to run in a browser tab to show its text" when a page builds its words with scripts (local file `src/core/messages.ts`). LinkPeek deliberately never runs a page's scripts on the device. Its offscreen parser reads fetched HTML without running it (local file `docs/decisions.md`, D25). A fix therefore has to run a browser somewhere else, or ask a service that does.

On the device, no route is confirmed. A hidden tab in the user's normal profile would send that user's cookies to the site, which breaks the no-cookies rule. Chrome's offscreen document, a hidden page inside the extension, can embed an iframe, but Chrome's documentation does not say whether a remote page loads there or which cookies it sends ([Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen)). A split-mode incognito process starts with an empty cookie store, which fits the rule. The documentation we read did not settle whether the user must allow the extension in private windows first ([Chrome incognito key](https://developer.chrome.com/docs/extensions/reference/manifest/incognito)).

Three candidates could do the rendering. Stars are GitHub's popularity count, not a quality score.

Sparticuz is built for serverless hosts, and its own setup pairs it with puppeteer-core, a library that drives the browser ([Sparticuz/chromium](https://github.com/Sparticuz/chromium)). The browser needs at least 512 MB of memory, and the bundle must stay under Vercel's 250 MB limit. The Hobby tier, Vercel's free plan, caps each call at 300 seconds on one processor and includes only 4 hours of active CPU time a month ([Vercel functions limits](https://vercel.com/docs/functions/limitations), [Vercel fair use](https://vercel.com/docs/limits/fair-use-guidelines)). A browser render uses far more CPU than a text summary, so that monthly allowance is a real limit. That is an inference, not something measured here. The article address would go to LinkPeek's Vercel function, Vercel would see it, and the article's host would see Vercel's network address rather than the reader's. The function stays Node and TypeScript, but it becomes a heavy one. The main risks are that it would fetch any address it is handed, which needs guards against private network addresses (a flaw called server-side request forgery, where a server is tricked into reaching internal systems), and that page scripts would run on LinkPeek's server. Whatever the browser returns is page text, so it must reach the card as plain text and never as instructions, as D25 already requires. Under the hard rules the route passes only with conditions. Each render needs a fresh browser with no cookies or logins. The code must never add stealth plugins, because those exist to get past bot checks. A login wall or challenge page after rendering counts as a failure to show, not as article text.

Vercel would be a named recipient of article addresses, and its privacy notice does not say how long it keeps request logs ([Vercel privacy notice](https://vercel.com/legal/privacy-policy)). The privacy note would have to name it. The backend already sends article text to Anthropic when a user picks LinkPeek's AI (local file `server/README.md`). This report did not check whether the privacy note covers that.

Jina Reader's default engine renders pages in a headless browser before it extracts text, so it removes the empty-page problem with no server of LinkPeek's ([Jina Reader](https://jina.ai/reader/)). The price is that every article address goes to Jina. Its legal page says Jina does not use request data to train its models, and it stores inputs only as needed to run the service by default. It also says Jina may keep operational and usage metadata, and it gives no retention period for request inputs ([Jina legal](https://jina.ai/legal/)). That page warns that its terms were written before Elastic acquired Jina AI and may no longer match current practice. Two options matter for privacy. The "Do Not Cache or Track" header asks Jina not to cache or log a request, and Jina suggests it for sensitive addresses. The Forward Cookie option must stay off. One rendering engine is Cloudflare-backed, which would make Cloudflare a second recipient whose terms were not read. Any Jina key would have to sit on the backend, never in the extension.

Playwright is the second choice. It is Apache-2.0 and has 98.2k stars ([Playwright](https://github.com/microsoft/playwright)). It also needs a Chromium binary on a serverless host, so it would use the same packaging as Sparticuz, and it would send the same addresses. Whether it fits Vercel's limits was not tested, which is why it ranks below.

Text extraction after rendering can stay with Readability, which sends nothing off the device. Defuddle (MIT, 9.7k stars, with a commit and a package release on 10 October 2026) is a newer alternative, but switching is not needed for this problem ([Defuddle](https://github.com/kepano/defuddle)). Its optional fallback sends X (Twitter) links to a third party, FxTwitter, unless that fallback is turned off, and FxTwitter's terms were not read.

The recommendation for this problem is not to build a renderer yet. The live test already planned in the decision log can count how many links come back empty, and D24 says to revisit server fetching if the permission step stops most people. If the empty-page count is high and the owner accepts a backend that fetches addresses, use Sparticuz on a paid Vercel plan, with address guards and a fresh browser for every request. Treat Jina as the no-server option only after its terms are checked against current practice.

## The permission fix is a product choice

No open-source extension we found solves the one-grant problem cleanly. The closest, Tabboost (MIT, 82 stars), asks for all sites at install, which the ground rules forbid ([Tabboost manifest](https://raw.githubusercontent.com/samzong/chrome-tabboost/HEAD/manifest.json)). Dark Reader has broad access by design, but the notes did not confirm that its own onboarding explains it ([Dark Reader](https://github.com/darkreader/darkreader)).

LinkPeek is further along than the notes said. The per-link flow asks Chrome for one site at a time, which is the complaint (local file `src/permission/permission.ts`). The settings page and the access window already offer "Allow all websites", which requests https://*/* and http://*/* in one step (local files `src/core/sites.ts`, `src/options/options.ts` and `docs/permissions.md`). The notes treated that grant as a future option. The owner's real decision is whether it should be the first thing people are asked.

The routes compare as follows. The all-sites grant gives one request and no repeat prompts for new sites. Chrome is expected to show one prompt for it, but nobody has counted, and the wording for these patterns is not confirmed ([Chrome permissions reference](https://developer.chrome.com/docs/extensions/reference/api/permissions)). It is also the largest grant. A list chosen at onboarding is smaller, but it asks again for every new site. Chrome's per-site request (addHostAccessRequest, Chrome 133 or later) still prompts once per site, and the docs do not describe its screen. The current activeTab approach needs a click each time and cannot read a link the user has not opened. A server fetch needs no extension permission at all, but it would send every address to LinkPeek's server, which reverses D24.

Two details matter for the all-sites choice. First, Chrome requires permission requests to come from a user gesture, and a button click is the documented case ([Chrome permissions reference](https://developer.chrome.com/docs/extensions/reference/api/permissions)). Whether a page opened at install counts was not tested, but a button on that page should count. Second, LinkPeek registers a content script, a script Chrome runs inside each matching web page, on every granted site (local file `src/core/sites.ts`). Under an all-sites grant, that script would load on every page the user opens. This report did not check what the script does beyond waiting for a click, and the answer shapes both the store review and the privacy note. Chrome's privacy fields ask for the narrowest permission that works ([Chrome Web Store privacy fields](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy)). Its Limited Use rule requires disclosure of browsing activity collected for a feature ([Chrome Web Store policies](https://developer.chrome.com/docs/webstore/program-policies/policies#limited_use)).

The recommendation for this problem is to keep per-site as the default, which matches the smallest-permissions rule. The all-sites choice should be one plainly explained offer, shown the first time a user meets a site they have not allowed, with a note that it can be turned off in Settings. That gives people who want one grant the result they asked for, and it keeps the decision with the user. Count the Chrome prompts in LinkPeek's own build before shipping, because nobody has yet. Whether a one-time offer is still too broad is a judgment for the owner, not something the code can settle.

Redirects have two parts. LinkPeek already follows ordinary redirects with its own fetcher, which is its own code and not a library (local file `src/core/retrieve/fetcher.ts`). For Facebook's link wrapper, the ClearURLs project publishes a pattern that pulls the real address out on the device, with no network call and no new permission. The add-on is LGPL-3.0, a copyleft licence in the GPL family that can require sharing changed code, so it gets a flag. Writing a short pattern of our own avoids copying anything, and a test can check it. The notes did not run the pattern against a live link. Google News links need a call to a Google endpoint. The only decoder found calls an unofficial internal endpoint, its licence was not verified, and it fails the named-third-party rule until that is checked ([googlenewsdecoder on PyPI](https://pypi.org/project/googlenewsdecoder), search snippet only). Shortened links such as t.co and bit.ly need no library. The extension can only follow them if it may read the shortener's host, which ties this problem to the permission decision.

Late-loading text has two fits. Readability already runs in LinkPeek's offscreen document. Its README does not say how it handles lazy-loaded images or noscript fallbacks, so that stays unconfirmed. metascraper reads Open Graph and JSON-LD metadata with fallbacks, which can supply a description when the body is empty ([metascraper](https://github.com/microlinkhq/metascraper)). Readability, pdf.js and metascraper send nothing off the device when run in the browser. metascraper's headless-browser service and paid cloud API are excluded.

PDFs are covered by pdf.js, which LinkPeek already uses and which reads PDFs that carry a text layer. Scanned PDFs need OCR, which is text recognition from images. tesseract.js (Apache-2.0) is the one candidate named here. Its speed, memory use and accuracy inside an extension were not tested, and it may download language data at run time, which was not checked ([tesseract.js](https://github.com/naptha/tesseract.js)). For pages that are not articles, Readability's isProbablyReaderable check is, by its own README, quick and rough, with false positives and negatives ([Readability](https://github.com/mozilla/readability)). Use it as one signal beside LinkPeek's word count, not as a verdict.

Consent walls and bot checks have no tool to adopt. Consent-O-Matic (MIT, 4.3k stars) and DuckDuckGo's autoconsent (MPL-2.0, 131 stars) choose accept or reject for the user. An "I still don't care about cookies" fork (GPL-3.0, from search snippets) accepts cookie policies when a site needs them. None is adopted. The ground rules as read here do not name consent banners, so the notes' "user-choice rule" is their reading, not written text. The no-click position still holds, because a click answers a question the user should answer and sits close to the no-bypass rule. The recommended behaviour is to detect the banner, say on the card that the text may be incomplete, and keep the banner's own words out of the summary. For bot checks, no tool should be used. FlareSolverr and cloudscraper exist to get past Cloudflare's checks, which the ground rules forbid. The ground rules already say that 403 errors, 429 rate limits, login pages and challenge pages are failures, and the decision log orders the checks so robot checks come first (local file `docs/decisions.md`, D26).

## Decisions for the owner, and what is still open

The first decision is whether the backend may fetch and render pages at all. That reverses D24, ends the promise that the server never receives page addresses, and needs a privacy note that names Vercel. Measure the empty-page rate first. The second is the Vercel plan. Hobby is for personal, non-commercial use only, and Vercel's fair-use page counts receiving payment to host a site as commercial use. A paid LinkPeek therefore needs Pro or Enterprise before it takes money ([Vercel fair use](https://vercel.com/docs/limits/fair-use-guidelines)). The third is whether a hosted service may see article addresses at all. If Jina is used, the privacy note must name it, and every request should send the header that asks it not to cache or log.

The fourth decision is the permission default: keep per-site and offer all-sites once, or make all-sites the first ask. Before choosing, the owner should check what the content script does on every page under an all-sites grant. The fifth is the redirect rule's licence. The owner can accept the LGPL-3.0 flag for the ClearURLs pattern, or have LinkPeek write its own pattern. The sixth is whether consent banners should get a written no-click rule in the ground rules, since the rules as written do not name them.

Several things stay open. Chrome's prompt count and wording for an all-sites request or a list are untested. So are whether an onboarding button counts as a gesture and how addHostAccessRequest looks to users. All of these need a test in Chrome on LinkPeek's own build. Whether Playwright or any renderer runs inside a Vercel function within its limits was not tested. Commit dates in this report come from GitHub's commits pages, read through a summarising tool and not checked by hand. Star counts are as fetched on 21 October 2026. The commit date is still unseen for Trafilatura, Browserless, Firecrawl, Crawl4AI, Consent-O-Matic, autoconsent, Dark Reader and Tabboost. Postlight's parser was last changed on npm in September 2024, and its npm record lists MIT, although the repo sidebar read earlier showed both Apache and MIT. GitHub search was not used under the session's scope rule, so discovery came from web search and direct repo pages, and better tools may be missing. Jina's pricing and rate limits were not read. Not checked: the Chromium binary's own licence, LinkPeek's privacy notice, how long Vercel keeps request logs in practice, and the cloud terms of Crawl4AI, Firecrawl, Cloudflare and FxTwitter. Crawl4AI and Firecrawl are excluded anyway.

The notes contained four errors that this report corrects. The all-sites grant already exists in LinkPeek. The backend never receives page addresses, which the permissions note did not make clear. Jina Reader does render JavaScript. The "user-choice rule" does not appear in the ground rules. The Vercel Hobby clause, which the notes had unconfirmed, is now confirmed on the fair-use page. Local project files (the decision log, the ground rules and the server README) were read on 21 October 2026.

## Conclusion

The three problems share one cost. Every fix that reads more pages either sends article addresses to a server or widens what the extension can reach. The on-device routes that avoid both are closed by the cookie rule or untested in Chrome, so privacy, not code, sets the limit. The owner can settle two questions first: whether the backend may see addresses, and how wide the default grant should be. The rest is small work, namely keeping Readability and pdf.js, adding a redirect pattern and showing clear failures.

The permission problem is also already half built. LinkPeek has an all-sites option, so the change is in what people are shown first, not in new code. That makes the default the most consequential choice in the whole set, because a grant a user did not expect is the one thing a store reviewer and a privacy-minded user would both notice.
