# Test on-device reading before any server

The best fixes are a Chrome test of reading JavaScript pages in a hidden frame, one all-sites permission offered when a card needs it, and clearer messages for most link failures. Server rendering should wait until the owner decides to send article addresses off the device. The hidden frame needs no new permission and sends nothing to LinkPeek, but it is untested, and sites that refuse to be embedded will still fail. The all-sites permission ends repeat prompts while keeping access optional, which fits the owner's rule, but it is the widest access Chrome offers, and the owner's own wording ("one grant after install") would ask before any feature needs it. Fix the options-page bug first, because it may silently lose per-site access when a user unticks "all websites." Most other failures need a message, a copy change or a small code change, and they send nothing new. Almost every Chrome, Google, vendor and standards claim below was read through a page-summarising tool, so quoted wording needs checking on the live pages, and no note read the talkSPORT article itself.

## Three answers, with their costs and data flows

Problem 1 is pages that build their text in JavaScript, so the card says the page needs a browser tab. Problem 2 is the repeat permission prompt. Problem 3 is every other way a link fails. Facts about LinkPeek come from its code and documents, which were read but not run. Facts about Chrome, Google, vendors and standards come from pages read through a summarising tool. Claims the notes mark unverified carry the word "unverified" in the text, and claims seen only in search results say "snippet only."

### Reading pages that build their text in JavaScript

The recommended next step is a test of a hidden frame. LinkPeek already runs a hidden extension page, called an offscreen document, to parse fetched HTML. The change is to load the article in an embedded page (an iframe) inside that hidden page, let the site's own scripts build the text, and read the result with a small script that Chrome injects into the embedded page. The embedded page should start with no cookies. Chrome calls this a credentialless iframe, and its blog says it has been on by default since Chrome 110 ([Chrome blog](https://developer.chrome.com/blog/iframe-credentialless)). The notes call this the most promising on-device route, and they call it untested.

The evidence is thin. A 2023 Chrome blog post says content scripts can run in offscreen frames ([Chrome blog](https://developer.chrome.com/blog/Offscreen-Documents-in-Manifest-v3)), and no note confirmed that this still holds in current Chrome (unverified). The method for reading the frame comes from a 2024 forum thread, where the person who asked wrote, "That's more of a workaround than a solution." The main limit is clear. A site that sends X-Frame-Options (an older header that refuses embedding, or allows only same-site embedding) or frame-ancestors (a newer header that lists who may embed the page) will refuse to load. The notes infer that an extension page counts as another site for these headers (unverified). Nobody measured how many news sites send them.

Comparable services take different approaches. Microlink says every request runs in a real Chromium instance before capture (vendor claim). Iframely and Diffbot did not document their method. Chrome has no extension interface that returns reader-mode text, so LinkPeek cannot borrow the browser's own reader.

The base design costs no new permission. The offscreen page, the scripting permission and the per-site host grant (Chrome's permission to read a website) already exist. The offscreen page would need a different stated reason, which is a code change. No server is involved, so there is no hosting cost. The costs fall elsewhere. Each hidden load runs the site's scripts, analytics and adverts for a link the reader never opened, and the notes could not check whether publishers object (unverified). The hidden page is shared by every read, so each frame needs a hard time limit, and a frame that navigates to another site must count as a failure. The notes also say that a store listing which does not explain background loading could be treated as hidden functionality. That is an inference and is untested. One design is ruled out for the first version. Stripping the frame-blocking headers with a declarativeNetRequest rule (Chrome's rule system for editing web requests) would apply across the browser unless it can be scoped, which would weaken frame protection on the user's own tabs. The notes call this the largest security cost in the design. No build-time estimate appears in the notes.

The hidden frame sends the article's site an ordinary page request from the user's browser, carrying the user's IP address and browser type, plus whatever the page loads. LinkPeek receives only the extracted text. If the credentialless frame works as described, no cookies go out. Whether the frame sends a referrer (the address of the page the user came from) is unverified, and the privacy text promises that none is sent.

The user-click route is the fallback. The user opens the article and presses LinkPeek's button, and Chrome's activeTab permission (temporary access to the one tab the user acted on) lets the card read it. It needs no new permission and is reliable, but it does not give a preview without opening the page. The notes suggest it for sites that refuse the hidden frame.

A server that runs a real browser would cover more pages. It would also send each opened address to that server and onward to whichever processor is used. That contradicts the privacy text and decision D36 in docs/decisions.md, which say the backend never receives a page's address. Any server that renders pages must check every address the browser requests, not only the first, because the browser follows its own redirects and loads sub-resources ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). No note confirmed how Vercel enforces that clause. The current backend fetches no pages, so this risk would be new. The notes say LinkPeek takes no payment today, and Vercel's Hobby plan bars receiving payment for a site ([Vercel fair use](https://vercel.com/docs/limits/fair-use-guidelines)).

Iframely and Microlink, also examined, are hosted preview services. Iframely's policy says it caches URL data for up to thirty days and calls customers' URL data "not considered private" ([Iframely privacy](https://iframely.com/privacy)). Microlink's policy names no retention period for submitted URLs. Its Pro plan works out at about $1.07 per 1,000 requests ([Microlink](https://microlink.io/html)).

### One grant at the moment of need

The recommended design keeps the permission optional and asks only when it is needed. When a card needs a site the user has not allowed, LinkPeek's window offers "Allow this site," "Allow all websites" and "Not now," as it already does. After one all-sites dialog, LinkPeek should not ask again. Of the options that end repeat prompts, this is the narrowest, because it uses the same permission as a setup button after install but asks only when a card needs it. It also fits the owner's rule to request optional permissions when the user acts (ground rule 34 in build-plan/00-ground-rules.md). How many dialogs Chrome shows for one request is unverified, and so is the dialog text. Google's help page gives the wording as "Your data on all the websites you visit," as read through the summarising tool ([Chrome Web Store help](https://support.google.com/chrome_webstore/answer/186213?hl=en)).

The owner's wording, one grant after install, is a different choice. The notes advise against it under the owner's own rule, because it asks before any feature needs the access. The one study found on permission prompts examined Android users in 2012. It found that 17% of people paid attention to permissions during installation ([Felt et al. 2012](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2012/EECS-2012-26.html)). That study is not about Chrome, and no study tests a prompt shown at the moment of need. A named list of sites still prompts for each new site. The newer addHostAccessRequest call (Chrome 133 or later) is also per site, and whether it needs a click is unverified.

The cost is the access itself. The notes found no read-only all-sites permission in Chrome's documents. Chrome's Web Store policy asks developers to request "the narrowest permissions necessary," and, where more than one would work, "the least access to data or functionality" ([Use of permissions](https://developer.chrome.com/docs/webstore/program-policies/permissions)). A reviewer will ask why per-site grants do not serve the feature, and the submission must answer that. The developer dashboard page warns that "Requesting broader permissions than necessary may cause your extension to be rejected," but that page is dated 2020. With an all-sites grant, Smart mode (LinkPeek's default setting, which scans pages) would show icons on every page unless the default changes (decision 4). The window and options text must say what LinkPeek reads, because Chrome's policy also bars misrepresenting what an extension does. No study tested that wording.

Two code points come first. The options page's "all websites off" path calls chrome.permissions.request after two await steps (points where the code waits for an earlier step to finish), and it discards any error. Chrome's docs say a request must come from a user gesture, meaning a real click or key press. If the gesture is lost during the waits, the call may fail with no message, and per-site access the user had granted may not come back. The notes mark this as a bug candidate that needs a Chrome test (unverified). The suggested fix is to make the request straight from the click, before any wait. Second, docs/decisions.md says broad access "slows Chrome Web Store review." None of the policy texts the notes read says that. Treat the claim as unsupported until a source is found, or remove it.

The grant sends nothing new. Chrome holds it on the user's device, and scanning runs locally. The notes say nothing leaves the browser unless the user turns on AI summaries (docs/decisions.md D35 and D36). Chrome's Limited Use rule bars collecting or using web browsing activity, except for a user-facing feature described prominently on the store page and in the product ([Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)). Scanning every page has to fit that exception, and the listing and privacy text must say so. Chrome also lets users set an extension's site access to "When you select the extension," which the notes call "On click." Chrome's docs give an extension no call that reads or sets that level, so a grant may exist while automatic access is off (unverified).

### Other failures mostly need a message, not a request

Problem 3 covers a dozen failure types. Most need wording or a small code change. The table gives the recommended handling for each, its cost and what it sends.

| Failure | Recommended handling | Cost | Sends off the device |
|---|---|---|---|
| Facebook link wrapper (a l.facebook.com/l.php link that carries the real address in a u= parameter) | Read the real address from the link on the device. Make no request. | Small code change and a test | Nothing |
| Short links (t.co, bit.ly) | Do not follow on hover or during a scan. Say "This is a short link. Open it to see where it goes." | Wording | Nothing today; following would contact the shortener, which probably counts a click for the link owner |
| Google News links | Say LinkPeek can't open these yet. Do not call Google's internal endpoints. | Wording | Nothing |
| Link lands on another article on the same site | Note the change, read the landing page, and skip the headline check | Small code change | Nothing |
| Consent or cookie walls (text held back until a choice is made) | Read what is there, say a consent request is showing, and never click "accept" | Detection to build and test | Nothing |
| Text that loads late | Keep "needs a browser tab." For infinite scroll, label the card "The first part of the page." | Wording | Nothing |
| PDFs sent as generic files | Detect by the file's first bytes ("%PDF-"). Keep the 15-page limit. | Small code change | Nothing |
| Pages that are not articles (video, product, social, front page) | Label the type and show the page's own description | Small code change and wording | Nothing; an official oEmbed lookup would send the link to the platform |
| Bot checks | Stop with "The site asked for a human check." No retry, no solving, no change of identity. | Test first, then add the Cloudflare header check | Nothing new |
| Login walls and paywalls | Keep the existing messages. Show no text from a login page. For paid articles, show the publisher's description only, with no feeds, AMP copies or archives. | Already built | Nothing |
| Dead links, error pages that return 200, and legal blocks (HTTP 451) | Keep the plain message for 404 and 410. Give error pages and 451 their own wording. No automatic archive fallback. | Wording, plus detection to test | Nothing |
| Embedded frames from another site | Say the article sits in an embedded frame from another site. Do not fetch it. | Wording | Nothing |

Three checks need new detection that must be tested before shipping: the Cloudflare challenge header, consent-wall detection and soft-404 detection. The notes found no code for consent banners, embedded frames or challenge headers. The PDF and same-host fixes are small, because the code already holds the body or the paths they need. A cookie notice inside the article may end up as the opening sentence, because Readability's class-name filter includes "gdpr" and "banner" but not "cookie" or "consent." That is an inference and needs a test page. The notes rank dead links as the most common failure. They rest that on Pew Research's figures, which are snippet only: about a quarter of pages that existed from 2013 to 2023 are no longer accessible ([Pew](https://www.pewresearch.org/data-labs/2024/05/17/when-online-content-disappears/)). Those figures describe the web in general, not LinkPeek's links.

## Decisions for the owner, most important first

1. The permission model. Three options are on the table: per-site grants (repeat prompts), one all-sites grant when a card needs it (recommended), and one all-sites request at install (the owner's wording). The install option asks before any feature needs the access, which goes against ground rule 34. The owner also has to decide whether an all-sites grant is acceptable under the smallest-permissions rule at all. If it is not, the realistic choices are repeat prompts or a named list that still prompts for each new site.

2. Hidden loads. Approve the hidden-frame tests now (Chrome tests 1 to 10). Decide whether the hidden frame ships only after those tests pass and the store listing says LinkPeek can read a page in the background. The notes found no published case on how reviewers treat hidden loading, so the owner may want to ask Chrome Web Store support before building.

3. Article addresses leaving the device. Recommended: not now. A server or hosted service would change the privacy text, the Web Store privacy disclosure and decision D36. Before any processor receives an address, the owner needs a written answer from Vercel on its acceptable use policy (if the fetch runs there), the processor's terms read and accepted, a data processing agreement (the contract a processor signs) where one is offered, and advice on UK data-protection law, which the notes did not check. The owner should also decide whether Vercel's non-commercial Hobby plan still fits.

4. Default scanning under an all-sites grant. Smart mode scans every page LinkPeek may read. The owner can make Manual the default once all sites are granted, or shrink the page script to a small loader that waits for the user to act. Under an all-sites grant, decision D17 ("sites are switched on one at a time") would no longer describe the product. Decide after Chrome test 16 measures the cost.

5. Cookie walls and consent banners. Recommended: detect them, say so, and leave the banner alone. Never click "accept" for the user. The EDPB's guidance gives an example, a forced "Accept cookies" button, that is not valid consent ([EDPB guidelines](https://www.edpb.europa.eu/system/files/documents/files/file1/edpb_guidelines_202005_consent_en.pdf)). Clicking "reject all" records a choice the user never made, and it writes a record on the user's device, which the notes read as possibly within the UK's cookie rule (unverified). The owner should approve detect-and-disclose only, or allow "reject all" as a per-site opt-in after legal review.

6. robots.txt. Robots.txt is a site's file of crawl rules. The notes do not show LinkPeek checking it today. They also disagree about Google. The link-failures note quotes Google saying its user-triggered fetchers "generally ignore robots.txt rules." The server note read Google's crawler overview and found no such statement, so check Google's live pages before citing either. OpenAI says robots rules "may not apply" to user-initiated actions ([OpenAI](https://developers.openai.com/api/docs/bots)). The standard, RFC 9309, covers crawlers and says its rules "are not a form of access authorization" ([RFC 9309](https://www.rfc-editor.org/rfc/rfc9309)). Decide whether a disallow for an article's path stops a card, and state the answer in the permission and privacy text.

7. Copies of free and paid articles, and archives. Recommended: use a publisher's feed or AMP copy only for a free article, when the page itself is free and the copy is the same article. Never use one for a paywalled article, which the no-bypass rule forbids. Archives such as the Wayback Machine should never run automatically, because that sends the link to another company. A link the user clicks is the owner's call.

8. Short links. Recommended: show the "open to see" message and do not follow the link. The alternative follows the redirect once the user grants the shortener's host. That needs a new permission, changes the privacy text (which says LinkPeek fetches "that one page from its own website"), and probably counts as a click for the link owner. Bitly's support page says free short links show an advert page first (snippet only).

9. Official lookups for video and social pages. oEmbed is a public lookup that returns a title and author without running the page's scripts. Official YouTube and X lookups would improve these previews, but each lookup sends the link to the platform. The notes did not check the current platform documents.

10. Measurement. Two choices. The first is whether to run a labelled list of 60 to 100 public URLs on a schedule from the project's public repository. That sends requests to third-party sites, so the owner should accept robots.txt checks and rate limits, which the existing live-check script lacks. The second is whether to send an opt-in, anonymous count of failure reasons to the project's server. That is the only route to population numbers. It needs privacy text changes, a new category in the Web Store form and a full Limited Use review, and it should default to off. The notes suggest deferring it until the labelled list exists.

11. Smaller calls. Approve the Facebook unwrap rule (fix 9 below). Approve the plain Google News message. Approve the wording for HTTP 451 and error pages, and decide whether 410 gets its own "removed" message. Decide whether to keep the unused @sparticuz/chromium and puppeteer-core lines in server/package.json, which commit e604861 added on 21 Oct 2026. The commit message says rendering "sends article addresses to the backend, so it stays off until the owner decides."

## What is still unknown and how to find out

The biggest unknown is how often each failure happens. No source gives a figure for news links. A 2023 academic study found that "43% of web pages are not strictly dependent on JavaScript," across 6,384 pages, with JavaScript switched off in the browser ([arXiv](https://arxiv.org/abs/2301.10597)). A 2026 report from Zyte, a scraping vendor, says 40.6% of landing pages "serve empty shells to HTTP scrapers," but it gives no test for that claim ([Zyte](https://www.zyte.com/sowa/2026/barriers/javascript)). The definitions differ, and neither covers news links. LinkPeek's own live check of ten pages found one JavaScript-built page (YouTube), a login wall and a paywall, and seven gave full text (docs/progress.md). That sample is too small to estimate a rate.

To find out, the owner can check the four Facebook links by hand. That takes under an hour, needs no build, and shows whether the talkSPORT case is a wrapper, a JavaScript page or something else. After that, a labelled list of 60 to 100 public URLs, run weekly, would show how often the "needs a browser tab" rule fires correctly. The notes estimate one to two days to build it and a few hours a month to keep it. A local counter of failure codes, with no hostnames stored, would show one user's mix, and it takes about a day to build. Public datasets such as the Web Almanac measure general web trends, not LinkPeek's links.

The second unknown is how many sites refuse embedding. A survey of news-site headers, with no rendering, would show it. That number decides whether the hidden frame is worth building, and the notes give no estimate. The third is the talkSPORT article itself. No note fetched it. The research tool's fetch of talksport.com's robots.txt failed, and its terms were not found. Whether the first HTML holds the text, and which headers the site sends, can be checked in Chrome's developer tools (Chrome test 1).

Fourth, vendors and the law. Vercel has not said how its acceptable use policy applies to a user-triggered fetch. Cloudflare's pages do not say whether Browser Run blocks private addresses or keeps data, and they give two concurrency figures (10 included, and 200 by default). Several hosted vendors' retention terms are unverified, and Diffbot's processing agreement appears only in a search snippet. The notes read the UK cookie rule (PECR regulation 6) through the summarising tool ([legislation.gov.uk](https://www.legislation.gov.uk/uksi/2003/2426/regulation/6)). The EU text of Article 5(3) and the Planet49 ruling could not be retrieved, because EUR-Lex returned empty pages. The French regulator's fine is known only from press reports, and the status of the EU Digital Omnibus reform after mid-October is unclear. A lawyer should review the cookie and processor questions before any build.

Fifth, the Web Store. The notes found no published review outcome for hidden loading or all-sites grants, and no test can settle a reviewer's view. The owner can ask Chrome Web Store support, or draft the listing text and permission justification first. The Limited Use exceptions beyond the first sentence of item 4 were not fully read.

Sixth, cost and tooling. The per-render costs rest on CPU time the notes did not measure. The Sparticuz Chromium package has not been tested with puppeteer-core 25, and its README says nothing about sandboxing. Before choosing any host, measure ten JavaScript-built pages, with the owner's approval, because the test sends real article addresses to that host.

Seventh, the other frequencies. The notes did not measure how often soft 404s, HTTP 451 responses, PDFs sent as generic files, geo-blocks, consent walls or per-site paywalls occur on news sites. Age-verification walls were not researched, and they will probably look like login walls. The fallback order of the consent tools Consent-O-Matic and autoconsent is unconfirmed.

Two points are unsettled across the notes. Google's robots.txt position conflicts (decision 6), and whether Facebook still wraps outbound links in 2026 rests on snippets only. Separately, every quote from Chrome, Google, vendors and standards needs checking against the live page before anyone cites it. The soft-404 signals, the consent-wall signals and the DataDome and PerimeterX markers are general knowledge or secondary sources, and no note tested them.

## What a Chrome test must settle

Run each test on LinkPeek's own build (the dist folder, not the test builds), on current stable Chrome and on Chrome 116, which is LinkPeek's minimum. Record the Chrome version. Use a test profile, local pages (scripts/serve-test-pages.mjs already serves some) and test cookies. Never use a real login.

1. The talkSPORT article first. Does the first HTML response hold the article text, and does the page show text after its scripts run? Record which response headers refuse framing and how long the text takes to appear. Do not try to pass any challenge. (Problem 1)
2. Hidden frame. Does a content script injected into an iframe inside LinkPeek's offscreen page run and read text on current stable Chrome? Confirm that it does nothing in the user's own tabs on that site and nothing outside the frame. Test on a local page before the talkSPORT article. (Problem 1)
3. Credentialless frame. Does it load from an extension page? Does the offscreen page need a cross-origin embedder setting (a manifest key that Chrome supports from version 93)? Does a test cookie set on a local server reach that server? Does a referrer go out? (Problem 1 and privacy)
4. Frame refusal. Do X-Frame-Options (DENY and SAMEORIGIN) and frame-ancestors headers stop the hidden frame, as the MDN pages describe? (Problem 1)
5. Header stripping. Does a declarativeNetRequest rule that removes those headers take effect on frames the offscreen page starts? Does it also loosen the same site in a normal tab? If it does, the rule must not ship as written. (Problem 1 and security)
6. Offscreen permissions and warnings. Does an offscreen cross-origin fetch fail with no host grant and work with one? Does a new offscreen reason, or any added permission, change the install or update warning, or require a new version? (Problems 1 and 2)
7. Timing and limits. Does a page that builds text on animation frames stall in a hidden frame? Does a hard time limit remove the frame? Does a redirect to another site count as a failure? (Problem 1)
8. Fallback click. After the user clicks LinkPeek's button, does script run on that tab with activeTab alone? Does it also run on a tab LinkPeek opens itself? (Problem 1, fallback)
9. Second tier. Does a background tab read a JavaScript-built page? Do cookies or storage the page writes survive the tab closing? Does Chrome discard the tab during a long session? (Problem 1)
10. Incognito. In spanning mode, can the background page run script in an incognito tab after the user turns on "Allow in Incognito"? Record Chrome's exact wording for that switch. (Problem 1, second tier)
11. Dialog count. In Settings, click "Turn on for all websites." Count the Chrome dialogs and record their text. Repeat with https only, with three named sites in one call, and with the same three sites in three calls. (Problem 2)
12. Repeat prompts. After one site is granted, does a later request that includes it prompt again? (Problem 2)
13. Options-page bug. Grant several sites, untick "all websites," and note whether the per-site grants come back, come back with a prompt, or disappear. Then make the fix (the request before any wait) and confirm it works. (Problem 2)
14. Install page. Does a button on the page LinkPeek opens at install count as a user action for the request? (Problem 2, the install option)
15. On click. With all sites granted and the setting changed to "When you select the extension," does the content script still run? What do chrome.permissions.contains (Chrome's check for a held permission) and the options page report? Does the grant appear under "Allowed sites"? (Problem 2)
16. Footprint. With an all-sites grant in Smart mode, how many icons appear on a normal page by default? Does Manual or Scan avoid scanning? How long does start-up take on a page with 1,200 links? (Problem 2 and decision 4)
17. Removal. After "all websites" is allowed, can each site be removed in Chrome? Is the help text "you can't change them after" accurate? Does a fresh install of the current build show any warning? (Problem 2)
18. Human check in a hidden frame or tab. Does a challenge page show, and does LinkPeek's challenge detector in diagnose.ts catch it? The route must stop and must not retry. Use a local page that sends the challenge header, not a live challenge. (Problems 1 and 3)
19. Challenge header. Can the extension's fetch read the cf-mitigated header (Cloudflare's marker for a challenge page) on a cross-origin response? (Problem 3)
20. Cookie notice. Use a fixture page with a banner inside the article element. Does Readability include the banner text in the opening sentence? (Problem 3)
21. Optional. Does addHostAccessRequest (Chrome 133 or later) work without a click, and does its grant appear under "Allowed sites"? Does chrome.pageCapture.saveAsMHTML on a hidden tab include the rendered text? Neither is on the recommended path.

## Fixes that need no research

These need code or copy changes, and no outside evidence. Each still needs the Chrome test where one is listed.

1. Move the all-sites restore request in src/options/options.ts (around line 105) so it runs straight from the click, before any wait, and show or log its error instead of discarding it. Confirm with Chrome test 13.
2. Remove the claim that broad access "slows Chrome Web Store review" from docs/decisions.md (D17), or replace it with the policy's own words.
3. Detect a PDF by its first bytes ("%PDF-") when the server sends the generic application/octet-stream type or no type. The type check is in src/core/retrieve/fetcher.ts (line 68), and the content-kind code is in diagnose.ts. Keep the 15-page limit and add a test.
